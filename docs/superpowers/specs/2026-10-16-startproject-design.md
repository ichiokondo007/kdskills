# kdskills / startproject 設計書

作成日: 2026-10-16
状態: 承認待ち(利用者レビュー前)

## 1. 目的

`kdskills` は、プロダクト開発の工程(プロジェクト開始 → 要件定義 → DB 設計 → 画面設計 → …)を
Claude Code のスキルとして束ねた、AI-DLC(AI-Driven Development Lifecycle)の独自版である。
1 プロジェクト = 1 リポジトリで、要件定義・DDL・画面設計などの成果物をそのリポジトリに蓄積する。

本書はその最初のスキル `startproject` を定める。`startproject` の役割は次の 2 つに限る。

1. プロジェクトの土台(フォルダ、`docs/`、`プロジェクト概要書.md`、Git の main と初回コミット)を作る
2. 利用者の頭の中を `プロジェクト概要書.md` に明文化する。埋まっていない項目から順に決めていく

後続の工程(要件定義、DB 設計など)は別スキルとして同じプラグインに追加する。本書の対象外。

## 2. 利用者と成功条件

- 利用者: 本人。自宅ホームラボなどの個人プロジェクトを複数持ち、別端末でも同じ手順で始めたい
- 成功条件:
  - `/kdskills:startproject hoge` で `hoge/` が作られ、main ブランチに `init` コミットがある
  - 概要書は「決まったこと」と「決まっていないこと」が一目で分かる
  - セッションを切っても、同じコマンドで未決の項目から再開できる
  - `kdskills` を `git clone` すれば別端末でも同じスキルが使える

## 3. プラグイン構成

リポジトリは `~/kdskills`。GitHub で管理する。

```
kdskills/
├── .claude-plugin/
│   ├── plugin.json        name: "kdskills", version: "0.1.0"
│   └── marketplace.json   name: "kdskills", plugins: [{ name: "kdskills", source: "./" }]
├── skills/
│   └── startproject/
│       ├── SKILL.md       手順書(日本語)
│       └── templates/
│           ├── プロジェクト概要書.md
│           └── gitignore
├── docs/superpowers/specs/   設計書(本書)
├── README.md              工程の全体像、各スキル、インストール手順
└── .gitignore
```

### 命名規約

- スキル名は英小文字のハイフン区切り(`startproject`、`db-design`)。呼び出しは `/kdskills:<name>`
- スキルが生成するファイル・フォルダは日本語名でよい。利用者が読む側は日本語、仕組み側は英語
- 各スキルの固定出力は `templates/` に置き、SKILL.md からは「テンプレートをコピーして埋める」と参照する。
  SKILL.md 本文にテンプレートを埋め込まない

### 試し方とインストール

- 開発中: `claude --plugin-dir ~/kdskills` で起動し `/kdskills:startproject` を使う
- 別端末: `git clone` → `claude plugin marketplace add ~/kdskills` → `claude plugin install kdskills@kdskills`
- コマンドの細部は実装時に公式ドキュメントで確認し、README に正確な手順を書く

### 検証方針

スキルの自動テストは作らない。ワークスペースで `/kdskills:startproject sample` を実際に走らせ、
期待どおりのフォルダ・文書・コミットができることを目で確認する。

## 4. `startproject` の動作

### 4.1 引数と前提

- `<name>` は必須。無ければ「プロジェクト名を教えてください」と聞いて止まる
- `<name>` は現在のディレクトリ直下のフォルダ名。英数字、ハイフン、アンダースコアのみ。それ以外は理由を示して止まる
- `./<name>` が無ければ新規モード、あれば再開モード

### 4.2 新規モード

1. 次を作る
   - `<name>/docs/.gitkeep`
   - `<name>/プロジェクト概要書.md`(テンプレートをコピー。全項目 `未着手`、日付は `date +%Y-%m-%d` の値)
   - `<name>/.gitignore`(テンプレート `gitignore` をコピー)
2. `<name>/` で `git init -b main` → 全部を `git add` → コミットメッセージ `init` でコミット
3. 「土台を作りました」と報告してから埋め込みフェーズへ

### 4.3 再開モード

1. `<name>/プロジェクト概要書.md` を読み、項目 1〜9 の状態を一覧で見せる(決定 / 検討中 / 未着手 の数とどの項目か)
2. 概要書が無い、または `## N.` 形式の項目見出しが揃っていない場合は「kdskills の概要書ではないようです」と止める。作り直さない
3. 埋め込みフェーズへ。対象は `検討中` と `未着手` の項目のみ

### 4.4 埋め込みフェーズ(両モード共通)

1. 新規モードのときだけ、最初に一度だけ聞く:
   「今、頭にあることを順不同で全部書いてください。決まっていないことも、候補や迷いもそのままで構いません」
   再開モードではこの質問を飛ばす
2. (新規モードのみ)答えを 11 項目に振り分けて概要書を更新し、「埋まった項目 / 空の項目」を一覧で見せる。
   再開モードでは 4.3 で見せた一覧がこれに当たる
3. 空の項目を項目番号の若い順に 1 つずつ聞く。1 メッセージ 1 項目。
   項目によっては選択肢や推奨を添える(技術スタックなら候補と判断軸を提示する)
4. 答えの扱い
   - 決まった → `決定` として本文を書く
   - 候補段階 → `検討中` として本文に「候補: A / B」「判断軸: …」の 2 行を必ず残す
   - 「飛ばす」「後で」→ `未着手` のまま次へ
5. 1 項目答えるごとに概要書へ書き込む(セッションが切れても進捗が残る)
6. 利用者が「ここまでで終わり」と言ったら、残りは聞かずに終了処理へ
7. 終了処理
   - 項目 10 `未決事項` の表を、`検討中` と `未着手` の項目名・状態・何が決まっていないかで書き直す
   - 項目 11 `次のアクション` が空なら 1〜3 個提案し、利用者に確認してから書く
   - 先頭の表(最終更新、決定/検討中/未着手の件数)を更新する
   - main 上で `docs: 概要書を更新` としてコミットする。worktree は使わない。概要書は main が正本

### 4.5 やらないこと

- `docs/` 配下のサブフォルダは作らない(後続スキルの仕事)
- GitHub へのリポジトリ作成や push はしない
- 概要書以外の文書(要件定義など)は作らない
- 既存フォルダを作り直したり、概要書の見出し構造を変えたりしない

### 4.6 エラー時の扱い

| 状況 | 対応 |
|---|---|
| `<name>` 未指定 | 名前を聞いて止まる |
| `<name>` に許可外の文字 | 理由を示して止まる |
| `git` が無い、`git init` 失敗 | フォルダと文書は残し、Git 部分だけ失敗したと報告して止まる |
| 再開モードで概要書が無い / 形式不一致 | 「kdskills の概要書ではないようです」と止める |
| `git commit` が identity 未設定で失敗 | 設定方法を示して止まる。概要書の内容は失われない |

## 5. `プロジェクト概要書.md` テンプレート

状態は見出し直下の `**状態**:` 行に書く。GitHub で読んでも分かり、スキルが機械的に拾う目印にもなる。
HTML コメントは使わない。

```markdown
# <name> プロジェクト概要書

| 作成日 | 最終更新 | 決定 | 検討中 | 未着手 |
|---|---|---|---|---|
| YYYY-MM-DD | YYYY-MM-DD | 0 | 0 | 9 |

状態の意味: **決定** = これで進める / **検討中** = 候補と判断軸あり、未確定 / **未着手** = まだ考えていない

## 1. 一言説明
**状態**: 未着手

(何を作るかを 1 行で)

## 2. 背景・課題
**状態**: 未着手

(なぜ今これをやるのか。困っていること、きっかけ)

## 3. ゴール
**状態**: 未着手

(「できた」と言える状態。できれば確認できる形で)

## 4. 利用者
**状態**: 未着手

(誰が、どんな場面で使うか)

## 5. スコープ
**状態**: 未着手

### やること
-

### やらないこと
-

## 6. 主要機能の候補
**状態**: 未着手

(1 行 1 機能。後で機能ごとに要件定義へ分解する)
-

## 7. 技術スタック
**状態**: 未着手

| 区分 | 選定 | 状態 | 候補 / 判断軸 |
|---|---|---|---|
| インフラ | | 未着手 | |
| アプリ | | 未着手 | |
| DB | | 未着手 | |
| 認証 | | 未着手 | |
| その他 | | 未着手 | |

## 8. 制約・前提
**状態**: 未着手

(既存資産、予算、期間、運用条件)
-

## 9. リスク・懸念
**状態**: 未着手

-

## 10. 未決事項
(終了処理でスキルが自動更新する。手で書いてもよい)

| 項目 | 状態 | 何が決まっていないか |
|---|---|---|

## 11. 次のアクション
-
```

### 規則

- 先頭の表の件数は項目 1〜9 の 9 個を対象にする。10 と 11 は状態を持たない
- 項目 7 は行ごとに状態を持つ。項目全体の状態は、全行 `決定` なら `決定`、
  そうでなければ行の中で重い方(`未着手` > `検討中`)
- 日付は実行時に `date +%Y-%m-%d` で取る。推測で書かない
- `検討中` の項目には「候補:」「判断軸:」の 2 行を必ず残す。再開時の問いの出発点になる
- `(...)` の説明文は、本文を書いたら消してよい

## 7. 将来の拡張(本書の対象外、構成の前提のみ)

- 後続スキルは `skills/<name>/` に追加し、`docs/` 配下に工程ごとのサブフォルダを作る
- 後続スキルは `feature/<工程名>` ブランチを worktree で切って作業し、ある時点で main へマージする。
  worktree の置き場所は後続スキルの設計で決める
- 項目 6 `主要機能の候補` の 1 行ずつが、要件定義スキルの入力になる
